# 从前端到后端：基于 CampusPlatform 的进阶学习路线

整理日期：2026-10-09。

这份路线基于 CampusPlatform 的核心代码、数据库迁移、测试文件和部署学习记录整理。本次只做了代码阅读，没有启动服务、运行构建或执行测试；下面的项目观察不代表所有功能已经通过运行验收。

## 3. 第一项：事务、并发与消息一致性

### 为什么优先学

[OrderService.java](../../campus-trade-server/src/main/java/com/campus/trade/campustradeserver/order/service/OrderService.java) 已经使用 `@Transactional`，通过条件更新把商品从在售改为锁定，并检查实际更新行数。这里适合深入理解多个请求同时操作一份数据时，系统如何保证正确。

### 学什么

- 事务的提交和回滚：哪些操作属于同一个事务，失败时哪些数据会恢复。
- MySQL 事务隔离、行锁和死锁：理解并发请求如何互相影响。
- 条件更新：在 SQL 中检查当前状态，再决定是否允许修改。
- 幂等：同一个操作重复执行时，不产生额外的业务影响。
- 消息发布确认、消费确认、重试和失败队列：理解每一步保证什么。
- 消息补偿与 Outbox：把业务数据和待发送消息放进同一个数据库事务，再由后续任务发送消息。

### 在项目里练什么

1. 两名买家同时购买同一件商品，确认只有一笔订单成功，商品状态正确。
2. 让付款和超时取消接近同时发生，检查订单与商品状态是否一致。
3. 重复处理同一条超时消息，确认不会重复释放商品或修改已付款订单。
4. 在测试环境模拟 RabbitMQ 不可用，观察下单结果、事务回滚和错误返回。
5. 分析“消息发送成功，但数据库事务提交失败”以及“发布确认超时，但消息实际已经到达”的处理方式。

当前下单方法在数据库事务中发送 RabbitMQ 消息。`@Transactional` 不会自动让 MySQL 与 RabbitMQ 一起提交或回滚；发布确认也不能保证数据库事务随后一定成功。这是需要理解和验证的边界。

### 掌握标准

- 能画出下单涉及的数据库更新和消息发送顺序。
- 能解释两人同时下单时，条件更新和数据库锁各起什么作用。
- 能解释付款与取消竞争时，哪些状态允许转换，哪些应拒绝。
- 能为重复消息和消息发送失败提出可验证的处理方案。

## 4. 第二项：Java 与 Spring 原理

### 学什么

- Java 集合、泛型、异常、`equals/hashCode`。
- 线程安全、共享变量、线程池，以及它们适用的场景。
- Spring 依赖注入、Bean 的创建和代理机制。
- 事务传播、回滚规则，以及 `@Transactional` 失效的常见原因。
- 请求经过过滤器、Controller、Service 和 Mapper 的过程。
- 阅读异常堆栈、设置断点和跟踪方法调用。

### 在项目里练什么

1. 选“创建订单”这一个接口，从请求进入到返回响应，逐步跟踪执行过程。
2. 解释 Service 的依赖为什么能被注入，以及事务是从哪里开始、在哪里结束的。
3. 在独立的小例子中比较“外部调用事务方法”和“同一个对象内部调用事务方法”。
4. 找一次自己遇到过的异常，沿着堆栈定位到具体代码，再解释原因。

### 掌握标准

能不依赖完整教程独立增加一个业务功能，说明关键注解和异常处理的作用，并在运行失败时定位问题。

如果 Java 基础主要是跟着 Spring Boot 教程顺带学的，就让这一项与订单练习并行；不需要一次学完所有高级知识。

## 5. 第三项：MySQL 查询与性能

### 项目中的入口

商品搜索使用了 `LIKE '%关键词%'`，普通 B-tree 索引通常不能有效加速这类搜索。商品图片保存为 Base64，并随部分列表查询返回；数据量增加后，需要评估它对存储、查询和网络传输的影响。

已有索引不代表所有查询都高效。是否需要调整，要根据执行计划和测量结果判断。

### 学什么

- `EXPLAIN`、联合索引、最左前缀、回表和排序。
- 分页查询的成本，以及深分页为什么可能变慢。
- 慢查询排查：区分数据库查询、应用处理和网络传输的耗时。
- 文件上传与对象存储：数据库保存文件地址，文件服务保存图片。
- 上传权限、文件类型与大小限制，以及无用文件清理。

### 在项目里练什么

1. 给测试库准备适量数据，分析商品列表和买家订单列表的执行计划。
2. 比较有无分类筛选、有无关键词搜索时的查询方式。
3. 根据查询条件尝试调整索引，记录调整前后的执行计划和耗时。
4. 比较列表返回完整图片与返回图片地址时的响应大小。
5. 设计图片上传接口，考虑上传成功但商品保存失败时如何清理文件。

### 掌握标准

能回答“接口慢在哪里”，提供执行计划或耗时证据，解释调整方案为什么有效，以及增加索引或缓存的成本。

## 6. 第四项：测试、权限与故障验证

### 当前起点

`src/test` 中目前主要是应用启动测试和认证 DTO 序列化测试；项目另外保存了手动接口与故障验收记录。后续应继续覆盖关键业务规则和异常路径。

沿用项目已有学习方式：接口通过 Postman/Apifox 验证，页面通过浏览器验证；不涉及 HTTP 的纯业务规则可以使用 JUnit。并发与真实依赖故障需要在独立测试环境中验证。

### 学什么

- 如何从业务规则整理正常、边界和失败用例。
- 身份认证、角色权限、数据归属权限各解决什么问题。
- JUnit 的基本断言，以及如何测试纯业务规则。
- 如何根据请求 ID、日志、消息状态和数据库记录定位问题。
- 依赖不可用时，何时可以降级，何时必须拒绝请求。

### 在项目里练什么

- 重复下单、付款、取消，以及非法的订单状态转换。
- 修改请求中的订单 ID，尝试访问其他用户的数据。
- 普通用户直接请求管理员接口。
- Redis 不可用时，分别观察公开缓存读取、登录认证和退出操作。
- RabbitMQ 发送或消费失败时，检查订单、重试和失败队列。
- 在事务中制造异常，检查相关表是否一起回滚。

可以从 [手动验收对照表](../manual-acceptance.md) 继续补充用例。每条记录至少包括：前置条件、操作、预期结果、实际结果、数据库状态和相关日志。

### 掌握标准

能证明正常流程和关键失败流程符合业务要求，并能复现问题、定位原因、验证修复。逐步把适合重复执行的纯业务测试保存下来，避免每次修改后都从头检查。

## 8. 第一个具体练习：两人同时下单

先从这一项开始，不同时开展整份路线。

准备两名买家和一件在售商品，在测试环境向同一件商品发起接近同时的下单请求。

预期结果：

- 只有一个请求成功创建订单。
- 另一个请求得到明确的失败结果。
- 数据库只有一笔本次成功创建的订单，商品处于锁定状态。
- 成功订单的买家、卖家和金额正确。

练习后回答：

1. 两个请求都可能先读到商品在售，为什么最后仍能限制一个成功？
2. 哪条 SQL 决定了谁能成功？为什么必须检查更新行数？
3. 如果商品已经锁定，但插入订单失败，商品会不会恢复？
4. 你用哪些请求结果、日志和数据库记录确认了结论？

一次手动实验只能验证该次执行结果，还需要结合 SQL 条件、锁和事务解释为什么设计能处理并发。掌握后，再进入“付款与超时取消同时发生”的练习。

## 10. 更完整的后端能力地图

前面的章节侧重当前项目的下一步。本节补充后续成长路线，覆盖 Java 后端常见的能力方向。学习顺序由基础、项目问题和目标岗位决定，不以是否听过某个技术名词决定。

“合格后端”的共同要求是：能独立交付业务功能，保证关键数据和权限正确，验证异常情况，排查运行故障，并与团队协作。不同岗位对微服务、Kubernetes、高并发和行业知识的要求不同，没有一份适用于所有岗位的工具清单。

### A. 基础必修：能够解释代码、数据和请求如何运行

| 方向 | 需要学习的内容 | 掌握标准 |
| --- | --- | --- |
| Java 语言与代码设计 | 集合、泛型、异常、时间、金额精度、接口与组合、常见设计模式 | 能独立实现业务逻辑，正确处理金额、时间和异常，避免为了套模式增加复杂度 |
| 并发与 JVM | 线程安全、锁、线程池、原子操作、内存结构、垃圾回收、线程与堆排查 | 能定位共享变量问题、线程阻塞和内存增长，并解释线程池配置 |
| Spring 与持久层 | Bean、依赖注入、代理、AOP、事务传播与回滚、请求处理链、MyBatis 参数绑定 | 能解释框架行为和事务边界，排查注解失效，安全地访问数据库 |
| 数据库 | 表设计、约束、索引、事务隔离、锁、执行计划、分页、连接池、迁移 | 能保证数据约束，解释查询成本和并发结果 |
| 网络与操作系统 | HTTP、TCP、DNS、TLS/HTTPS、超时、进程、线程、文件权限、端口与磁盘 | 能区分应用、代理、网络和系统故障，并使用基本命令排查 |
| 数据结构与复杂度 | 数组、链表、哈希表、栈、队列、树、基本排序与查找、时间和空间复杂度 | 能选择合适的数据结构，识别不必要的重复查询和高成本循环 |

基础算法有助于理解程序成本。若准备求职，再根据目标岗位单独练习算法题；刷题不能替代业务实现和工程实践。

项目已经覆盖其中一部分。后续应通过独立修改、解释和验收确认掌握程度，不把“依赖已经引入”当成“已经学会”。

### C. 进一步成长：分布式、微服务与容器平台

| 方向 | 为什么学 | 重点内容 |
| --- | --- | --- |
| Redis 深入 | 缓存可能不一致，也可能在高流量下失效 | 缓存穿透、击穿与雪崩、过期与淘汰、热点键、大键、持久化、故障恢复；有需求后再学分布式锁及其失效边界 |
| 消息队列深入 | 发送成功、消费成功和业务成功是不同阶段 | 发布与消费确认、重复消费、有限重试、失败队列、积压、顺序、Outbox 和补偿 |
| 分布式系统 | 多个应用协作会出现部分失败 | 超时、幂等、重试、限流、熔断、最终一致性、补偿、跨服务数据处理 |
| 微服务 | 支持按业务边界独立发布、扩容和团队分工 | 服务边界、服务调用、网关、发现与配置、故障隔离、调用追踪、契约兼容 |
| Kubernetes | 在多台机器上管理容器应用 | Pod、Deployment、Service、Ingress、配置与 Secret、探针、资源请求与限制、滚动更新、回滚、扩容 |
| 系统设计与容量 | 根据业务量、可靠性和成本选择方案 | 访问量与数据量估算、瓶颈、缓存策略、高可用、恢复目标、成本和方案取舍 |

微服务的概念值得理解，实际拆分能力可以在单体应用基础扎实后练习。Kubernetes 的应用部署与排查适合随后学习；集群安装、网络与存储运维、复杂权限管理属于更深入的平台方向，可按岗位需要继续。

### D. 按业务选择：遇到需要时深入

| 方向 | 适用场景 | 可学习的技术与能力 |
| --- | --- | --- |
| 全文搜索 | 复杂搜索、相关性排序、聚合 | Elasticsearch 或 OpenSearch、索引构建、数据库变更同步 |
| 实时通信 | 聊天、在线通知、实时状态 | WebSocket、SSE、连接管理、断线重连、消息补发 |
| 定时与批处理 | 超时兜底、报表、对账、批量处理 | 定时调度、分批处理、重复执行保护、失败续跑 |
| 支付与交易 | 真实支付、退款、资金核对 | 签名与验签、金额校验、回调幂等、对账、补偿、审计 |
| 数据库扩展 | 容量或可靠性出现明确需求 | 主从复制、读写分离、复制延迟、高可用；必要时再研究分区与分库分表 |
| 其他数据存储 | 关系型数据库不适合某类数据需求 | 根据查询与一致性要求评估 MongoDB 等，不为了增加技术种类替换 MySQL |
| 云服务 | 使用托管数据库、存储和运行平台 | 对象存储、IAM 权限、网络隔离、负载均衡、托管服务、成本管理 |
| 深入平台工程 | 负责大量服务的发布与运行 | Helm、GitOps、Kubernetes 网络与存储、服务网格等，按平台职责选择 |

这些方向不是全部完成后才能承担后端工作。应根据项目问题和目标岗位选择；同一类工具通常先学一个代表，再比较其他方案。

## 11. 微服务和 Kubernetes 的具体学习顺序

### 第一步：两个应用通过网络协作

保留 CampusPlatform 作为主要单体应用，另建独立学习样例，用两个 Spring Boot 应用练习服务调用。不急着拆分现有全部业务。

先验证调用成功，再验证超时、对方不可用、重试和重复执行。重点理解：调用超时不代表对方没有完成操作。

### 第二步：学习微服务配套能力

| 能力 | 解决什么问题 | 可以选择的工具 |
| --- | --- | --- |
| 网关 | 请求路由与部分通用策略 | Spring Cloud Gateway |
| 服务发现 | 实例地址变化后的查找 | Nacos 等 |
| 服务调用 | 发起跨服务请求 | Spring HTTP 客户端或 OpenFeign |
| 配置管理 | 管理不同服务与环境的配置 | 配置中心或运行平台配置 |
| 故障保护 | 控制超时、流量与故障影响 | Resilience4j 或 Sentinel |
| 观测 | 跟踪调用、查看错误率与资源状态 | OpenTelemetry、Micrometer、Prometheus、Grafana 等 |

这些是学习例子，不是一套必须同时安装的工具。Spring Cloud 是配套工具集合；理解服务边界与故障处理，才能合理使用这些工具。

### 第三步：把无状态应用部署到 Kubernetes

从一个 Spring Boot 应用开始，练习声明实例数量、提供访问入口、注入配置、设置探针与资源限制。随后验证实例退出后的替换、新版本滚动更新和回滚。

Pod 是基本调度单元；Deployment 管理期望版本和实例数量；Service 提供稳定访问入口。先理解这三者，再增加 Ingress、自动扩容等内容。

Secret 是配置对象，安全还依赖访问权限、集群存储保护和密钥管理，不能仅凭对象名字认为敏感信息已安全。

数据库的迁移、备份和恢复仍需要单独设计。Kubernetes 不会自动解决业务错误或保证数据一致性。

考虑电脑性能，先用轻量环境验证一个应用，不同时运行完整微服务、监控和集群组件。

## 12. 分阶段判断自己学到了哪里

| 阶段 | 可以用什么成果判断 |
| --- | --- |
| 能独立开发 | 不依赖完整教程，完成一个含表结构、接口、权限和异常处理的业务需求 |
| 能可靠交付 | 验证并发、重复请求和依赖故障，部署应用，并完成一次数据恢复 |
| 能排查与优化 | 根据日志、执行计划、线程或内存信息定位问题，提供优化前后证据 |
| 能设计多服务协作 | 解释拆分理由，处理跨服务超时、重复执行、部分失败和数据补偿 |
| 能使用容器平台 | 在 Kubernetes 上部署、观测、更新、回滚并排查应用 |

对当前项目，仍从订单并发和事务开始，随后推进 Java/Spring、数据库、测试与安全、观测与部署。再用独立样例学习多服务协作和 Kubernetes，根据目标岗位补充搜索、实时通信、支付或平台工程。
