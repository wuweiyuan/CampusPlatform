## 今天讲解到哪里

已完成本项目以下内容的逐步讲解，不再停留在上一份记录中的 CMD/ENTRYPOINT：

- Dockerfile 复制规则：来源为目录时复制其内容；来源末尾是否带 `/` 不改变此规则。目标写 `.mvn/` 才保留目标 `.mvn` 层级，不能简单合并成 `COPY .mvn/ mvnw pom.xml ./`。`.`、`./` 是当前工作目录，`/` 是构建环境根目录。
- Nginx：`server`、`listen`、`server_name _`、`root`、`index`；精确匹配 `/api` 与前缀 `/api/`；代理请求头；静态资源缓存、入口文件重新验证，以及 Vue history fallback。
- Compose 从头解释：`services`、`image`、`build.context`、Dockerfile 路径、重启策略、环境变量、命名数据卷、绑定挂载、端口映射、健康检查和依赖条件。
- 数据库账号：`MYSQL_USER` 与 `MYSQL_PASSWORD` 用于业务账号，`MYSQL_ROOT_PASSWORD` 用于数据库管理员；区别于网站用户和 Linux 用户。初始化环境变量不会自动修改已有数据卷里的账号密码。
- Spring Boot 配置链路：`.env` → Compose 替换变量 → 容器环境变量 → Spring Boot 数据源/Redis/JWT 配置；不修改 JAR 或 application.yml 文件本身。
- Redis 启动命令、容器内 Shell、`$$` 转义、密码认证、AOF、数据卷及 PING/PONG 健康检查。
- 数据卷实际名称通常带项目名前缀，如 `deploy_mysql_data`。多个项目均用 `deploy` 可能冲突；可用 `-p` 区分，但当前项目直接改名会使用另一套数据卷，旧数据不会自动迁移。
- `service_healthy` 是 Compose 固定条件值，依赖健康检查；启动依赖不保证运行中故障会自动级联处理，unhealthy 本身不触发 restart 策略。
- `config --quiet`、`up -d --build`、缓存复用、`ps`/`ps -a`、curl、页面加载与登录/受保护操作的验收链路。
- `up -d` 不会仅因源码变化自动重新构建已有镜像；源码或 Dockerfile 修改后使用 `up -d --build`。`--build` 执行构建流程但复用缓存，不等于每次从头编译。

最后确认：本项目的 Docker 主要配置和部署流程已经基本讲完，不代表 Docker 所有知识都已覆盖。接下来应转入部署实践或回答用户具体疑问，不要自动从 Dockerfile 开头重复讲解。
