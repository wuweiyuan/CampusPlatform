## 1. 代码入口与已讲内容

- 下单入口：[OrderService.java](../../campus-trade-server/src/main/java/com/campus/trade/campustradeserver/order/service/OrderService.java) 的 `createOrder(Long buyerId, Long productId)`；Controller 通过 Spring 注入的 `OrderService` 调用它。
- 主流程：查商品和校验买家 → 条件更新商品 `ON_SALE → LOCKED` 并检查影响行数 → 插入订单 → 查订单详情 → 在事务提交前发送超时消息并等待发布确认 → 登记提交后清理热门商品缓存 → 返回结果。
- 2026-10-09 已逐段讲到方法结尾。用户明确确认理解 `insertOrderWithRetry` 中异常被哪个 `catch` 捕获，以及数据库自增主键回填到 `Order` 对象；`insert` 返回的 `1` 是影响行数，不是订单 ID。
- 本次讲了 `@Transactional` 的边界：Controller 调用经过 Spring 事务代理；`BusinessException extends RuntimeException`，未处理的异常传出时默认回滚数据库事务。商品已锁定而后续订单插入失败时，商品更新也会回滚。被 `catch` 捕获且重试成功的 `DuplicateKeyException` 不等于立即回滚。
- [ProductMapper.java](../../campus-trade-server/src/main/java/com/campus/trade/campustradeserver/product/mapper/ProductMapper.java) 的条件更新包含 `WHERE id = ... AND status = 'ON_SALE'`。两个请求即使都曾读到在售，也只有成功更新 1 行的请求可以继续创建订单；更新 0 行必须停止，否则同一商品可能生成两笔订单。两个事务可同时运行，但对同一行的更新由数据库锁协调。

## 2. 2026-10-15 两人下单实验

### 准备与第一次失败

- 测试商品 `id=15`，卖家 `id=2`，两个不同买家各持有效 Token。初次发送两条请求均得到 HTTP 401、业务 `code=401`。随后两个 Token 调用 `/api/auth/me` 均返回 200；使用 `productId:null` 调用下单接口返回参数错误 400，排除了 Token 无效这一解释。
- 后端日志显示真正异常为 `AmqpConnectException: java.net.ConnectException: Connection refused`，发生在 `OrderTimeoutMessageProducer.send`，当时后端无法连接 `localhost:5672`。未处理异常后的接口响应被误报为 401，不能据此认定请求未进入 `createOrder`。
- 第一次失败后，用户查询到商品仍为 `ON_SALE`，`orders` 中没有该商品的订单，符合数据库事务回滚后的状态。Docker Desktop 中另有一个正在运行的独立 RabbitMQ 容器，但本机 `127.0.0.1:5672` 当时连接被拒绝。用户随后启动项目 Compose 的 `rabbitmq` 服务，`nc -vz 127.0.0.1 5672` 显示连接成功。后续服务状态需要重新检查，不能假定一直运行。

### RabbitMQ 可连接后的成功实验

- 对同一商品 `15` 从两个后台任务尽量同时发送 `POST /api/orders`。买家 A 得到 HTTP 400、`code=3003`、`当前商品状态不允许下单`；买家 B 得到 HTTP 200、`code=0`，订单 `id=18`、`buyerId=3`、`sellerId=2`、`amount=99999.00`、`status=PENDING_PAYMENT`。
- 用户随即查询数据库：商品 `15` 为 `LOCKED`；`orders` 中该商品只有 1 条记录，字段与买家 B 的成功响应一致。这里记录的是实验当时的状态；超时消息后续消费后状态可能变化，本次没有再次查询。
- 对应请求日志：B 成功请求于 `11:02:25.890` 结束，`durationMs=675`，`requestId=92f2b103-632b-413e-b7f2-3d173ac84e7a`；A 失败请求于 `11:02:25.893` 结束，`durationMs=679`，`requestId=e58c5b93-d124-4205-805e-2b719a56cd25`。按结束时间和耗时估算，两个 HTTP 请求约在 `11:02:25.214–.215` 开始，处理时间重叠。A 的 HTTP 请求可能略早开始，但 B 获得了成功的条件更新。
- 这些证据支持“时间重叠的两次请求最终只成功创建一笔正确订单”。日志没有记录每条 SQL 的执行和等待时间，**不能证明** A 曾等待 B 的行锁，也不能证明两人最初都读到了 `ON_SALE`。若要直接观察行锁等待，需要另做受控的双事务实验并在等待期间查看 MySQL 锁等待信息。

## 3. 消息、事务与超时规则的接续学习

- 当前 `createOrder` 在数据库事务内先插入订单，再调用 `OrderTimeoutMessageProducer.send`，方法返回后 Spring 才尝试提交 MySQL。发布确认的最长等待 5 秒，不等于等待订单超时。`@Transactional` 不会把 RabbitMQ 和 MySQL 合成一个事务：RabbitMQ 连接失败会抛异常并使 MySQL 回滚；反过来，RabbitMQ 已接收的消息不会随 MySQL 回滚而自动撤回。
- 超时消息先进入延迟队列，队列 TTL 配置为 30 秒。消费者调用 `cancelExpiredOrder`；订单不存在时直接返回。若消息已发送但数据库回滚，消费者查不到订单并返回。另一个**仅推演、未实测**的极端时序是：消息到期时下单事务仍未提交，消费者看不到订单并正常返回，原事务稍后提交，可能留下没有这条超时消息可再处理的 `PENDING_PAYMENT` 订单。当前订单代码未见定时扫描兜底。
- 2026-10-15 讨论了两种方案：保留 MQ 并定时扫描过期待付款订单作兜底；或在本项目订单量较小时只用定时任务处理超时。当天未修改代码。2026-10-16 随后开始学习 Outbox，代码进度见下文；定时扫描方案尚未实现。重复触发 `cancelExpiredOrder` 时，订单状态的条件更新和事务使状态变化只成功一次。
- 付款与超时取消都以订单 `PENDING_PAYMENT` 为条件更新。先付款成功则订单 `PAID`、商品 `SOLD`；先取消成功则订单 `CANCELLED`、商品 `ON_SALE`，后来的付款失败。当前 `payOrder` 只检查状态，不检查创建时间；超过 30 秒但尚未取消时，付款仍可能成功，因此 30 秒不是当前付款接口严格执行的截止时刻。
- `orders.created_at` 由数据库在插入时填写，不是提交时间。用它计算 30 秒，若事务提交很慢，会缩短买家实际可见的付款时间。讨论了严格截止时间需要先确定计时起点；前端实际收到响应的瞬间后端无法准确获知，通常应由服务端给出明确的截止时间并在响应中返回。此前举出的带 `created_at > NOW() - INTERVAL 30 SECOND` 的付款 SQL 只是讲解示例，**不是当前项目代码**。

## 5. Outbox 学习与代码进度

- 解释了 `waitForConfirmsOrDie(5000)`：等待 RabbitMQ 发布确认，成功则继续，拒绝确认或超时则抛异常。它不等待消费者完成，也不代表 MySQL 提交。若消息已到达但确认超时，当前 `send` 异常会导致下单数据库事务回滚；已发布消息不会被撤回，之后消费者查不到订单便返回。该确认超时情形与数据库提交失败情形均只分析了代码，没有制造故障实测。
- Outbox 的目标是让“订单”和“需要发送消息的记录”在同一个 MySQL 事务中保存，提交后由后台任务发送；发送结果不确定时可能重复发布，因此仍依赖消费者的重复处理能力。这是学习路线中的消息补偿主题。
- 用户要求助手代写建表文件，已新增 [V7__create_order_timeout_outbox.sql](../../campus-trade-server/src/main/resources/db/migration/V7__create_order_timeout_outbox.sql)。表名 `order_timeout_outbox`；字段有 `id`、`order_id`、`due_at`、`status`、`attempts`、`created_at`、`sent_at`；`order_id` 有唯一约束，`status, id` 有索引。只做了文件回读和版本号检查，没有执行应用 V7 的操作，数据库表是否存在未查询验证。
- 用户随后明确要求 Java 代码由自己照着写，助手给完整代码并讲解、检查。助手曾代建 Mapper，已在用户纠正后撤回，随后由用户重新手写。目前磁盘上的 [OrderTimeoutOutboxMapper.java](../../campus-trade-server/src/main/java/com/campus/trade/campustradeserver/order/mapper/OrderTimeoutOutboxMapper.java) 已是带 `@Mapper` 的接口，方法名已改为 `insertPending`，带 `@Insert` SQL：

  ```sql
  INSERT INTO order_timeout_outbox (order_id, due_at)
  VALUES (#{orderId}, TIMESTAMPADD(SECOND, #{timeoutSeconds}, CURRENT_TIMESTAMP))
  ```

- 已帮助定位用户把 `interface` 写成 `class` 导致无方法体报错，以及方法名 `insertPend` 与约定名称不一致的问题。解释了 `Long` 可为 `null`、与 `Order.id` 一致；`long timeoutSeconds` 是必填秒数。
- 最后解释了 `due_at`：数据库当前时间加上 `timeoutSeconds`，表示计划检查订单超时的时间。例如 `14:00:00 + 30 秒 = 14:00:30`。保存它是为了后续发送任务晚发消息时仍可使用原计划时间；后续发送逻辑必须真正使用剩余时间或处理已到期事件，不能继续无条件延后 30 秒。它不是当前付款接口已实现的严格付款截止字段。
- **实现尚未完成：**`OrderService.createOrder` 仍直接调用原来的 `orderTimeoutMessageProducer.send(order.getId())`，没有注入或调用 Outbox Mapper；没有发送任务、发送状态更新或重试实现；没有改造延迟消息以使用 `due_at`。现有运行中的 Docker 镜像不会因为源码文件写入就自动包含这些改动。本次未重新构建、部署或运行 Java 编译、自动化测试。
