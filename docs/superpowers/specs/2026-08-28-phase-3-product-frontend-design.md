# 阶段 3 商品前端设计

## 目标

完成商品分类与商品的前端闭环：公开商品浏览、详情、发布、编辑与我的发布；同时将阶段 2 已完成的认证和基础页面统一为校园市集视觉，但不改变已有认证与权限行为。

## 路由与权限

`AppLayout` 成为整个商品体验的统一外壳，不再在父路由上要求登录。

| 路由 | 页面 | 登录要求 |
| --- | --- | --- |
| `/` | 商品广场 | 否 |
| `/products/:id` | 商品详情 | 否 |
| `/products/new` | 发布商品 | 是 |
| `/products/:id/edit` | 编辑商品 | 是 |
| `/my-products` | 我的发布 | 是 |
| `/profile` | 个人中心 | 是 |

现有全局前置守卫继续处理 `requiresAuth` 和管理员角色。布局根据认证状态显示相应导航：未登录用户看到登录、注册；登录用户看到发布、我的发布、个人中心和退出。

## 前端边界与数据流

新增 `src/api/category.ts` 和 `src/api/product.ts`，统一承载分类、商品、分页及请求负载 TypeScript 类型。页面只调用 API 函数，不直接使用 Axios。

商品广场以 `categoryId`、`keyword`、`page`、`pageSize` 为状态来源。提交搜索、选择分类、重置条件均将页码重设为 1，再请求 `GET /products`。商品卡片只使用列表接口字段，图片为空时显示分类色块占位。

商品详情以路由 ID 请求 `GET /products/:id`，并直接使用服务端返回的浏览量。商品详情只支持公开浏览；收藏和下单不属于本阶段。

发布和编辑使用同一表单页面。编辑通过公开详情加载初始值，随后以 `PUT /products/:id` 完整更新。提交前客户端检查标题 2–60 字、描述 10–2000 字、正数且最多两位小数的金额；选择图片时检查 JPEG、PNG、WebP 和不大于 2 MB，并转换为单个 Data URL。未选择图片或主动删除图片均提交 `imageBase64: null`。后端仍是最终校验者。

我的发布以关键词、状态和分页请求 `GET /products/mine`。只有状态为 `ON_SALE` 的记录显示编辑和下架；下架前二次确认，成功后刷新当前结果。编辑时若后端返回 403 或状态限制，显示服务端消息后离开编辑页。

## 页面与视觉系统

采用“效率目录”布局：暖米白页面背景、墨绿色结构色、珊瑚橙强调价格和主要操作，以细边框、纸张感卡片和清晰的内容密度表达校园市集气质。

商品广场顶部提供搜索和发布入口，分类筛选紧邻搜索，商品以响应式网格卡片呈现；桌面保留侧栏和更宽的内容区，窄屏收拢导航与筛选，保持单列或双列卡片和可触控操作。

登录、注册、个人中心、403、404 与基础布局改用同一套颜色、字号、按钮与表面层次。它们既有的表单校验、验证码倒计时、错误提示、认证存储和路由跳转均保持不变。

## 错误处理与反馈

每个异步页面具备加载、空内容和请求失败状态；请求失败沿用 `getErrorMessage` 提取服务端消息。发布、编辑和下架显示提交中状态，成功后给出 Element Plus 消息反馈并导航或刷新。图片类型、大小与表单字段在提交前显示可理解的中文提示。

## 验证

实现遵循测试优先：为新增可独立测试的 API 参数转换与图片校验提取纯函数，先写失败测试再实现。最后用项目声明的 Node `20.19.5` 运行完整类型检查与生产构建，并手动验证：匿名商品广场/详情、登录保护、发布、编辑、下架、跨账号访问和图片校验。

## 非目标

- 不修改后端接口、数据库结构或已执行的 Flyway 迁移。
- 不实现收藏、下单、订单、管理员分类管理或商品重新上架。
- 不暂存、提交或修改 Git 历史。
